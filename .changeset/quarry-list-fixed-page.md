'@stoneforge/quarry': patch

Serve `list()`/`listPaginated()` pages without materializing the whole match set. `SELECT DISTINCT` is now only emitted when a tag filter forces a join (`elements.id` is unique, so `DISTINCT` was a no-op that made SQLite build a temp b-tree over every matching row before applying `LIMIT`), and the count query uses `COUNT(*)` in that no-join case. `list()` no longer runs the O(n) `COUNT` pass at all — it only needs items — while `listPaginated()` still reports exact `total`/`hasMore`. Combined with the new ordering indexes in `@stoneforge/storage`, the default path (no tag filter, ordering by `created_at`/`updated_at`) reads a page straight from the index in every filter shape: `EXPLAIN QUERY PLAN` shows no `USE TEMP B-TREE FOR DISTINCT` and no `USE TEMP B-TREE FOR ORDER BY`, so a fixed page costs O(offset + limit) instead of O(table size).

Ordering semantics: when sort keys differ, results and page membership are unchanged, and the full result set for any filter is identical. The order of rows that share a sort key **changes**: it was never defined (it fell out of whichever query plan SQLite picked — ascending rowid from the old sort-based plan on some paths, reversed rowid on index-scan paths such as unfiltered `includeDeleted`), and every ordering now states an explicit deterministic tiebreaker instead: `ORDER BY <col> <dir>, rowid <dir>` — tied rows come back in ascending rowid order for `asc` queries and descending rowid order for `desc` queries, so pagination is stable (no row skipped or repeated across pages). The same tiebreaker was applied to `search()`, `searchChannels()` and the sync exporter's `getAllElements()`. The SQL construction is exported as `buildListQuery(filter, { includeCount })`; the query plan, the old-vs-new result equivalence and the tiebreaker are pinned by `list-query-plan.bun.test.ts`, which runs the pre-change query against the pre-change index set and compares results across equal-timestamp fixtures in both directions and at every pagination boundary.
