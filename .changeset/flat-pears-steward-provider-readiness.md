Fix silent merge-steward death spiral when an agent's provider cannot run sessions. A provider can be installed and still fail every turn — the codex CLI starts threads and then rejects each request with `401 Unauthorized` when it has no credentials, so a merge steward configured for it spawned, died ~15s later, and was resumed by orphan recovery until `stewardRecoveryCount` hit 3 and the merge was marked failed with only "Steward recovery limit reached" as the reason. Three changes:

- **Provider readiness gate.** `AgentProvider` gains an optional `getReadinessIssue()` probe; the codex provider implements it by checking for `~/.codex/auth.json` (or `$CODEX_HOME/auth.json`), `OPENAI_API_KEY`/`CODEX_API_KEY`, and any `[model_providers.*].env_key` that is set. `spawnMergeStewardForTask()` and merge-steward orphan recovery now refuse to spawn when the probe reports an issue, log it once per agent to the operation log (`sf log -c steward`) with the actionable message, and — unlike a genuine recovery — do **not** spend `stewardRecoveryCount`, since this is an environment problem, not a stuck task. Probe results are cached for 30s so recovery polls don't shell out to the CLI every cycle.
- **Why a session died is now recorded.** The spawner captures the terminal provider error (`session.lastError`) and the session manager persists it as `terminationReason: "Provider error: …"` plus a `lastError` field on the session-history entry, and writes it to the operation log on exit. When merge recovery gives up, `mergeFailureReason` now includes that error (e.g. `… last steward session failed: unexpected status 401 Unauthorized …`) instead of naming only the retry budget.
- **Steward resume validity.** `recoverOrphanedStewardTask()` no longer resumes `orchestrator.sessionId` blindly: the ID is only resumed when the task's own session history attributes it to a steward. A worker-owned ID (left over from before the steward claimed the task) is cleared and the steward fresh-spawns instead of attaching to the worker's conversation. Metadata writes along the recovery path re-read the task first so they no longer clobber the `stewardRecoveryCount` increment with a stale copy.
